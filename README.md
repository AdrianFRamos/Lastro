# Lastro

Lastro is the hackathon primitive for **persistent identity and verifiable custody of a physical asset**, starting with cattle.

The core flow is:

```text
physical RFID
→ ESP32-C5 Station
→ StationEvent[276]
→ ECDSA P-256
→ Rust Agent + durable SQLite outbox
→ Rust API + PostgreSQL projection
→ custodian wallet
→ Secp256r1 + Lastro Solana program
→ AnimalState/RfidBinding PDAs
→ independent browser verifier
```

The only domain transitions are `ORIGIN`, `TRANSFER`, and `REIDENTIFY`.

## Repository status

The software protocol path is implemented in source and protected by executable tests or explicit environment-gated integration tests:

- exact `StationEvent` encoding, RFID/Station/event hashing, action semantics, P-256 verification, and `EvidencePackage` validation;
- reader-independent ESP32 Station state machine, event construction/signing, and serial framing;
- Solana `ProtocolConfig`, `AnimalState`, and `RfidBinding` state transitions with exact Secp256r1-to-`StationEvent` binding;
- Rust Agent serial transport, durable SQLite outbox, retry/idempotency, and HTTP delivery;
- Rust API registration, capture coordination, cryptographic evidence admission, PostgreSQL persistence, wallet transaction preparation, confirmed transaction registration, finalized Solana confirmation, projection update, and evidence export;
- Wallet Standard browser transaction validation/signing and explicit A/B/C operator switching;
- independent browser verification of physical evidence, Station signature, identity continuity, custody continuity, and canonical Solana state;
- full-stack system and Playwright contracts for the hackathon flow, stale-custodian rejection, network retry, recovery, verifier validity, and evidence tampering.

Environment-gated tests are not considered passed merely because their source is implemented. Run the appropriate gate with the declared infrastructure and record its result.

The one intentionally unbound production edge is the **physical RFID reader adapter**. The ESP32-C5 board entrypoint and native USB Serial/JTAG Agent transport are wired; reader polling, raw bus access, framing, integrity checks, and canonicalization remain isolated behind the RFID adapter boundary. The repository does not contain a reader manufacturer/model, electrical pinout, wire framing, checksum rule, or captured frames. `docs/HARDWARE.md` defines the evidence required before that adapter can be implemented without inventing hardware facts.

Hardware, Devnet, eFuse, and real browser-wallet-extension interoperability remain **NOT VERIFIED IN AN ENVIRONMENT THAT DOES NOT PROVIDE THOSE dependencies**. Deterministic Playwright wallets validate the Wallet Standard integration contract; they do not prove a specific installed wallet extension.

## Frozen hackathon stack

- Rust 1.98.1 / edition 2024.
- Anchor 1.2.0 and the repository-pinned Solana toolchain.
- LiteSVM for deterministic on-chain protocol tests.
- ESP-IDF 6.1.x for ESP32-C5; Unity for target-based component tests.
- Axum + Tokio + SQLx 0.9 for API/Agent.
- PostgreSQL 18.x for the local projection store.
- Vue 3.5 + Vite 8 + TypeScript 6.0.2.
- Solana Kit + Kit RPC/Wallet plugins + Wallet Standard.
- `@noble/curves` 2.4.0 for portable browser P-256 verification.
- Vitest + Vue Test Utils for unit/component tests; Playwright for browser E2E.

Primary sources and consulted versions are listed in `docs/SOURCES.md`.

## Toolchain and dependency bootstrap

Run the read-only toolchain check first:

```bash
make doctor
```

Python repository/vector checks use the pinned development dependencies:

```bash
python3 -m pip install -r requirements-dev.txt
python3 -m pytest -q
python3 scripts/check_vectors.py --verify-only
python3 scripts/spec_check.py
```

Resolver lockfiles must be generated by the official pinned package managers, never written by hand or copied from unrelated versions. On a connected development machine with Rust 1.98.1, Node 24.21.0, and npm 11.19.0:

```bash
scripts/bootstrap_dependencies.sh
```

That command verifies the committed root `Cargo.lock` with Cargo's locked resolver, generates `chain/Cargo.lock` and `package-lock.json` with the pinned resolvers, refreshes `MANIFEST.sha256`, and leaves all outputs for review/versioning.

## Full local development

The complete software path can run locally with no real SOL and no browser-wallet extension. The local environment uses the real `solana-test-validator`, the real Lastro Anchor program, generated Wallet A/B/C keypairs, the real API/Agent, and the isolated hardware simulator. No local success bypass is added to production source.

```bash
make local-demo-doctor
make local-demo-init
make local-demo-up
```

Run the fresh full-system gate with deterministic Wallet Standard actors:

```bash
make local-demo-test
```

Use `make local-demo-test-headed` to watch the Playwright browser run. A real installed wallet such as Phantom remains a separate Devnet interoperability gate; the production frontend still discovers wallets through Wallet Standard.

All local identities, ledger data, tokens, logs, and artifacts stay under the gitignored `.lastro-local/` directory. See `docs/LOCAL_DEVELOPMENT.md` for setup, lifecycle commands, security boundaries, and the Local -> Devnet -> production transition model.

## Solana program identity

The repository does not include a private deployment key or a fictitious Program ID. After installing the official toolchain, run:

```bash
make bootstrap-program-id
```

The script generates `chain/target/deploy/lastro-keypair.json`, derives its public address, updates `declare_id!`, and runs `anchor keys sync`. The keypair remains gitignored and must be backed up securely; only the public address belongs in versioned deployment configuration.

## Implementation and validation order

1. `crates/lastro-protocol`: bytes, hashes, signatures, evidence, vectors.
2. `firmware/station`: physical reader adapter → canonical RFID → signed event.
3. `chain`: canonical state and Secp256r1 binding.
4. `services/agent`: serial + durable SQLite retry boundary.
5. `services/api`: evidence admission, capture/transaction submission/finalization, projection/export.
6. `apps/web`: Wallet Standard flow, operator console, independent verifier.
7. G3 full local flow.
8. G4 Devnet validation.
9. G5 three-run demo stability.
10. Physical hardware/eFuse gates only after their prerequisites are real.

Never convert an unavailable external dependency into a mocked success claim. Detailed commands, environment variables, and acceptance criteria are in `docs/TESTING.md` and the test source itself.
